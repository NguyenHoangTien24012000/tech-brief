#2 🔴 Phải đọc · 🛍 Shopify · — · ⭐⭐⭐

POS UI extensions 2026-10: Cart API mutation sẽ reject nếu POS không xác nhận đã ghi, thiếu try/catch là handler dừng giữa chừng Breaking

Trước đây các mutation của Cart API trong POS UI extension luôn resolve, dù POS có áp dụng thay đổi hay không. App không phân biệt được write đã ăn hay bị bỏ, nên có thể hiện "đã áp discount/phí" trong khi giỏ hàng không đổi. Từ API version 2026-10, mutation sẽ reject trừ khi POS báo thành công. Đây là breaking change cho app nâng lên 2026-10.

Phạm viTheo từng extension, dựa vào api_version khai báo, không theo store
Không ảnh hưởngExtension ở 2026-07 trở về trước
Mutation bị đổibulkCartUpdate, removeLineItem, applyCartDiscount, addCartCodeDiscount, removeAllDiscounts, setCustomer, removeCustomer, các mutation line item property/discount/selling plan
MớiupdateLineItemQuantity có từ 2026-10, reject ngay từ bản đầu

Hai thông báo lỗi cần phân biệt

  • "POS refused the cart update. The cart was not changed.": POS từ chối, giỏ không đổi, ví dụ thu ngân đã chuyển sang bước thanh toán. Retry có thể thành công khi giỏ được sửa lại được.
  • "POS could not confirm the cart update.": không rõ kết quả, có thể đã ghi một phần. Phải đọc lại cart trước khi retry.
  • Mutation vẫn có thể reject vì lý do khác (discount không hợp lệ, thiếu customer), nên chỉ so khớp message khi thật sự cần tách hai trường hợp trên.

Rủi ro khi nâng version

  • Rejection không được catch thì phần còn lại của handler không chạy: UI render sau write, cleanup như tắt loading. Hậu quả là spinner treo hoặc bỏ qua bước xác nhận.
  • App nào đã bọc try/catch hoặc .catch() thì handler đó sẽ chạy khi write không được xác nhận, thay vì tiếp tục như thể thành công.
  • Chưa kịp sửa thì giữ extension ở 2026-07; version này chạy tới hết support window.
Mẫu xử lý rejection từ Shopify
try {
  await shopify.cart.applyCartDiscount('FixedAmount', 'Winter discount', '5.00');
  setDiscountApplied(true);
} catch (error) {
  setDiscountApplied(false);
  showToast('Could not update the cart. Try again before payment.');
}
👉 Vì sao quan trọng: App loyalty/discount có POS extension (đổi điểm lấy discount, gắn customer vào giỏ) đang dựa vào việc mutation resolve. Nếu trừ điểm của khách sau khi gọi applyCartDiscount mà write bị bỏ, khách mất điểm mà không được giảm giá. Bản 2026-10 sửa đúng lỗ hổng đó, nhưng chỉ khi code xử lý reject.
✅ Nên làm: Grep POS extension: `shopify.cart.` → bọc try/catch từng call; chỉ trừ điểm/ghi log sau khi mutation resolve; với lỗi "could not confirm" thì đọc lại cart rồi mới retry. Xong mới đổi api_version = "2026-10".

#3 🔴 Phải đọc · 🛍 Shopify · — · ⭐⭐⭐

POS 11.15: Discount.amount của discount phần trăm giờ trả về % (25) thay vì số tiền (50), áp dụng cho MỌI API version Breaking

Shopify POS 11.15 sửa giá trị Discount.amount cho discount loại Percentage để khớp với hợp đồng của Cart API. Trước đây một discount 25% trên line item $200 trả amount: 50 (số tiền bị trừ). Từ 11.15 trả amount: 25. Khác với tin trên, thay đổi này không phụ thuộc API version: giữ api_version cũ cũng không tránh được.

Ví dụ25% trên $200: POS ≤11.14 trả 50, POS 11.15+ trả 25
Áp dụngDiscount cart-level và line-item: manual, app-applied, automatic có type: 'Percentage'
Không đổiFixedAmount và Code (kể cả mã giảm theo % có type: 'Code')
API versionMọi version, theo phiên bản app POS trên thiết bị

Những chỗ bị ảnh hưởng

  • State hiện tại và subscription của Cart API: lineItems[].discounts, cartDiscount, cartDiscounts, và contextual API cartLineItem.
  • Bản sửa cũng chặn một lỗi ngược: trước đây khi extension đẩy cart state qua bulkCartUpdate, số tiền phân bổ của discount % có thể bị hiểu nhầm thành phần trăm.
  • Shopify nêu rõ các chỗ cần sửa: hiển thị tiền tệ, tính tiền tiết kiệm, điểm loyalty, và tích hợp coi amount của Percentage là tiền.

Cần xử lý cả hai hành vi

  • Thiết bị POS chưa lên 11.15 vẫn trả số tiền. Nếu extension hỗ trợ POS 11.14 trở về trước thì phải xử lý cả hai cách hiểu cho tới khi thiết bị được nâng cấp.
  • Test discount % cart-level, line-item, automatic và mọi luồng bulkCartUpdate trên POS 11.15 trở lên.
👉 Vì sao quan trọng: App loyalty tính điểm hoặc hiển thị "bạn đã tiết kiệm X" từ Discount.amount sẽ tính sai ngay khi cửa hàng cập nhật POS, không cần app deploy gì. Đây là kiểu lỗi lặng lẽ, chỉ phát hiện khi merchant khiếu nại.
✅ Nên làm: Tìm mọi chỗ đọc `.amount` của discount trong POS extension; rẽ nhánh theo `type === 'Percentage'` để tính tiền từ % × giá line; viết test cho cả giá trị kiểu cũ và mới.

Decision model lên dòng chính: OpenAI Decisions API public beta (nhanh ~10x Responses API) và Strands Decider 2B mã nguồn mở chạy local ~115ms Mới

Sau khi TypeSafe AI ra Jev đầu tháng, "decision model" (còn gọi system-one model) thành một loại API mới: không sinh văn bản tự do mà chỉ chọn trong tập đáp án định sẵn hoặc chấm điểm, nên nhanh và rẻ hơn nhiều. Hôm qua OpenAI mở public beta Decisions API (384 điểm HN), còn đội Strands Agents phát hành Strands Decider 2B mã nguồn mở (274 điểm HN).

OpenAI DecisionsEndpoint POST /v1/decisions, model duy nhất gpt-6-luna, nhận text + ảnh
GiáChỉ tính input: 10 cent/triệu token (Jev: 4,2 cent)
3 loại câu hỏipredicate (xác suất 0–1), choice (một giá trị trong danh sách), score (trung bình có trọng số các mức)
Strands Decider 2BQwen3.5-2B bỏ LM head, thay pointer head ~1M tham số + LoRA rank 16
Latency localTrung vị ~115ms trên RTX 3090, ~153ms trên M3 MacBook

OpenAI Decisions API

  • Một request gồm model, evidence chung (text hoặc message có ảnh) và danh sách câu hỏi; mỗi câu có name riêng để khớp với mảng answers trả về. Câu trả lời có thể là refusal.
  • Ảnh phải là base64 data URL; không nhận URL HTTP hay file_id. SDK cần JavaScript 7.30.0, Python 3.26.0 trở lên. OpenAI dự kiến GA trong vài tuần.
  • Khi cần sinh object theo JSON schema riêng hoặc gọi tool thì vẫn dùng Structured Outputs/function calling của Responses API.
  • Simon Willison đã nhờ GPT-6 Astra đọc tài liệu và viết plugin llm-openai-decisions.

Strands Decider 2B

  • Pointer head chấm điểm hidden state tại từng vị trí option so với vị trí <answer>, nên luôn ra một đáp án hợp lệ, kèm điểm độ tin cậy mà API LLM frontier không cung cấp. Đổi lại, model không giải được bài phức tạp và không dùng cho code, chat, tóm tắt.
  • Đứng thứ 3/33 model hạng 2B trên JevBench (accuracy + Brier score), đúng 100% bài dễ. Bản phát hành là v19; code, weights, dữ liệu train đều công khai.
  • Ví dụ trong repo: trước khi agent gọi get_weather, decider trả lời 2 câu yes/no (tham số có dựa trên lời người dùng không, có quá sớm để gọi tool không). Kết quả Proceed/Deny/Confirm/Guide qua InterventionHandler.before_tool_call, nên agent hỏi lại thành phố thay vì đoán bừa.
Phân luồng khiếu nại bằng Decisions API (Node.js)

  model: "gpt-6-luna",
  input: "I was charged twice for my order.",
  questions: [{
    type: "choice",
    name: "department",
    instructions: "Which department should handle this complaint?",
    choices: [
      { value: "billing", description: "Payments, invoices, and refunds." },
      { value: "technical", description: "Problems using the product." },
      { value: "shipping", description: "Delivery and tracking." },
      { value: "other", description: "Requests outside these categories." }
    ]
  }]
});
👉 Vì sao quan trọng: Nhiều chỗ trong app đang gọi LLM chỉ để lấy một nhãn (phân loại ticket hỗ trợ, kiểm duyệt review, chọn template email). Decision model trả nhãn kèm xác suất, nhanh hơn và rẻ hơn, và có ngưỡng rõ ràng để quyết định khi nào cần người xem.
✅ Nên làm: Chọn 1 luồng phân loại đang dùng LLM sinh JSON, thử chuyển sang Decisions API với câu hỏi choice, so độ chính xác và latency trên vài trăm mẫu thật.

#5 🟡 Nên biết · 🛍 Shopify · — · ⭐⭐

Customer Account API thêm giới hạn 3.000 request/phút cho mỗi khách trên mỗi store, dùng chung cho mọi app Mới

Customer Account API giờ giới hạn mỗi customer trên một store ở 3.000 request mỗi phút. Hạn mức này dùng chung giữa tất cả app cài trên store đó, tức app của bạn có thể bị throttle vì app khác gọi nhiều cho cùng một khách. Shopify nói traffic người mua bình thường thấp hơn nhiều, nên đa số app không cần sửa.

Ngưỡng3.000 request/phút cho mỗi customer, mỗi store
Chia sẻChung cho mọi app gọi Customer Account API trên store
Khi vượtHTTP 429 Too Many Requests, lỗi THROTTLED, header Retry-After
Quan hệ với giới hạn cũÁp dụng thêm, không thay thế rate limit theo cost

Retry đúng cách theo Shopify

  • Nhận diện được response HTTP 429.
  • Đọc header Retry-After trong response.
  • Chờ đúng khoảng thời gian đó rồi mới retry, không retry ngay hoặc dồn dập.

Trường hợp dễ chạm ngưỡng

  • Extension trên trang tài khoản khách gọi API trong vòng lặp hoặc polling liên tục cho một khách.
  • Nhiều app cùng render block trên customer account cho cùng một khách: lượng gọi cộng dồn vào một hạn mức chung.
👉 Vì sao quan trọng: App loyalty thường có widget trên trang tài khoản khách (số điểm, lịch sử, phần thưởng). Code polling hoặc retry không có backoff có thể làm khách thấy lỗi, và khó debug vì nguyên nhân có thể từ app khác.
✅ Nên làm: Rà client gọi Customer Account API: bỏ polling không cần thiết, thêm xử lý 429 đọc Retry-After.

Admin API 2027-01: appDowngradeAccessScopes hạ optional write scope xuống read mà không mất quyền đọc Mới

Từ Admin GraphQL API 2027-01, app dùng Shopify-managed installation có thể gọi appDowngradeAccessScopes để thay optional write scope bằng read scope tương ứng. Trước đây cách duy nhất là appRevokeAccessScopes, và nếu read chỉ có được nhờ write thì revoke write sẽ mất luôn quyền đọc. App hiện tại không cần làm gì.

VersionAdmin GraphQL API 2027-01 trở lên
Điều kiệnScope nằm trong optional_scopes, là write scope có read scope tương ứng
Không đượcHạ scope bắt buộc (required)
ValidationMột scope lỗi → cả request bị từ chối, scope giữ nguyên; write chưa được cấp thì bị bỏ qua

Khác gì appRevokeAccessScopes

  • Revoke write cũng xoá read nếu read chỉ được cấp qua write. Downgrade giữ lại read.
  • Mutation chỉ tác động tới installation của chính app gọi nó.
  • Field downgraded trả về các write scope đã đổi thành công; lỗi validation nằm trong userErrors.
Hạ write_products xuống read_products
mutation {
  appDowngradeAccessScopes(scopes: ["write_products"]) {
    downgraded { handle }
    userErrors { field message }
  }
}

Diễn biến mới quanh bản công bố toán học của OpenAI: Scott Aaronson gọi là "Mathocalypse", có chứng minh Unique Games Conjecture nhưng gần như chưa ai đọc hiểu Đọc sâu

Hôm qua bản tin đã đưa việc OpenAI công khai hàng trăm bản thảo toán học do model nội bộ tạo. Một ngày sau, bài HN gốc lên 1.228 điểm, 1.402 bình luận, và nhà khoa học máy tính Scott Aaronson viết bài phản hồi chi tiết. Vợ ông, nhà lý thuyết độ phức tạp Dana Moshkovitz, đã theo đuổi Unique Games Conjecture (UGC) cả sự nghiệp, và trong số 372 kết quả có một chứng minh cho UGC.

Quy mô theo AaronsonModel được thử khoảng 8.000 bài, giải ~5% sau một lần chạy ~3 giờ compute mức GPT-Pro
ModelModel nội bộ mới nhất, không phải hệ thống hàng nghìn agent; có thể ra cho khách trả phí trong vài tháng tuỳ hội đồng an toàn
Kiểm chứngCó Lean certificate cho UGC và một số kết quả khác, không phải tất cả
HN1.228 điểm, 1.402 bình luận

Đọc chứng minh của AI như thế nào

  • Dana mô tả bài viết như "do người đang phê thuốc viết": nhiều đoạn không rõ, trích dẫn thường không liên quan, khó đọc nếu không có AI hỗ trợ. Bà phải hỏi GPT-6 Astra để gom các claim rải khắp bài thành phát biểu completeness/soundness.
  • Chứng minh UGC dùng một loại code mới, xây đệ quy kèm noise test, không phải long code hay short code quen thuộc. Kèm theo là chứng minh trực tiếp độ khó xấp xỉ tối ưu cho Max Cut và mọi CSP mà không cần đi qua UGC.
  • Danh sách Aaronson chú ý: L=BPL, Fourier transform và nhân số nguyên nhanh hơn O(n log n), nhân ma trận O(n^(9/4)), Parity không thuộc QAC0. P≠NP thì không có.

Hai cách công bố

  • Kiểu OpenAI: thả bản thô ra công chúng, khiến giới nghiên cứu đua nhau đọc hiểu, phần việc có thể vất vả và ít được ghi công.
  • Kiểu Anthropic: một ngày trước đó, Virginia Williams và Josh Alman công bố 3SUM trong O(n^1.9992) và APSP trong O(n^2.9995), với ý tưởng then chốt từ model của Anthropic. Anthropic để hai người viết bản đã "tiêu hoá" và trả thù lao cho họ, đổi lại công ty được chọn ai làm người truyền đạt.
👉 Vì sao quan trọng: Nhiều người dùng code do agent viết mà không đọc kỹ, và bài này cho thấy cùng vấn đề ở mức cực đoan: kết quả có thể đúng (có Lean check) nhưng người không hiểu được. Bộ kiểm tra máy chạy được đang trở thành thứ quyết định độ tin cậy.

Docker Agent: định nghĩa agent và nhóm agent bằng YAML, chạy bằng `docker agent run`, chia sẻ qua OCI registry

Docker đưa docker-agent lên trang nhất HN (176 điểm): một runtime để build, chạy và chia sẻ AI agent bằng file YAML khai báo, không cần viết code. Điểm khác biệt là cách đóng gói: agent được push lên OCI registry và pull về chạy ở đâu cũng được, giống image container.

Cách dùng

  • Nhiều agent chuyên trách tự giao việc cho nhau (multi-agent); file YAML version được trong git.
  • docker agent new tạo agent bằng hội thoại; docker agent run myorg/agent:tag chạy agent lấy từ registry.
  • Đội Docker dùng chính docker-agent để phát triển docker-agent (golang_developer.yaml). Có thu thập telemetry ẩn danh.

      - type: mcp
        ref: docker:duckduckgo

docker agent run agent.yaml
