#1 🔴 Phải đọc · 🏗 Software engineering · 🔥🔥🔥 · ⭐⭐⭐

Simon Willison: dịch vụ tính tiền theo usage cần hard budget cap MẶC ĐỊNH, vì agent khiến hoá đơn bất ngờ dễ xảy ra hơn Mới

Coding agent và personal agent (theo cách gọi của Simon là 'coding agent bọc trong UI bớt đáng sợ hơn') giúp dựng code gọi API trả phí, host web app hay hệ thống tự scale storage/compute dễ hơn nhiều. Hệ quả: rủi ro thức dậy thấy một service chạy mất kiểm soát đã đốt vài trăm đến vài nghìn đô qua đêm. Simon cho rằng hard budget cap phải trở thành tính năng mặc định của mọi dịch vụ pay-by-usage. Bài lên 587 điểm HN với gần 300 bình luận.

Lập luận chính

  • Soft cap ('vượt $X thì gửi email') vô dụng khi email đến lúc nửa đêm và service vẫn tiếp tục tiêu tiền trong lúc bạn ngủ.
  • Phản biện thường gặp: doanh nghiệp không muốn app trả lỗi chỉ vì vượt ngân sách. Simon cho rằng phần lớn doanh nghiệp và cá nhân thích lỗi hơn là hoá đơn bất ngờ trên $10.000.
  • Ai muốn 'sống nguy hiểm' vẫn có thể tắt cap, nhưng phải chủ động tick vào một ô kiểu 'Remove the budget cap… I will be responsible for subsequent charges'.

Ngành đang dịch chuyển

  • AWS là dịch vụ Simon muốn thấy nhất: nhiều người từ chối dùng AWS cho dự án cá nhân vì sợ một service chạy mất kiểm soát làm họ phá sản.
  • Trải nghiệm AWS mới (16/09) cho đặt spend limit theo tháng; chạm limit thì project bị tạm dừng trong tháng đó. Trang tài liệu ghi đang mở cho số lượng khách hàng giới hạn.
  • Google Cloud ra Spend Caps từ tháng 7, cho đặt trần tài chính theo tháng trên từng service của project.

Vai trò của agent

  • Simon mong agent tự ưu tiên gợi ý nhà cung cấp có hard budget cap.
  • Agent cũng nên cảnh báo người mới khi họ chuẩn bị deploy lên dịch vụ không có trần chi phí.
👉 Vì sao quan trọng: Backend app Shopify thường gọi nhiều dịch vụ trả theo usage (Cloud Functions, Firestore, LLM API, email/SMS). Một vòng lặp lỗi, một webhook bị retry dồn dập hay một agent chạy thử trên project thật có thể đốt tiền rất nhanh. Câu hỏi 'nếu chạy sai cả đêm thì tốn bao nhiêu?' cần có câu trả lời trước khi sự cố xảy ra.
✅ Nên làm: Kiểm tra từng dịch vụ trả phí của app (cloud project, LLM API key, email/SMS) xem đang có hard cap hay chỉ có budget alert. Với LLM API key dùng cho agent/thử nghiệm, tách key riêng và đặt spend limit cứng.

#2 🔴 Phải đọc · 🛍 Shopify · — · ⭐⭐⭐

ShopGym: Shopify biến storefront thật thành sandbox shop có thể reset để test shopping agent MớiĐọc sâu

Train và đánh giá shopping agent rất khó: sản phẩm, giá, layout store liên tục đổi; bot detection và throttling làm gián đoạn lượt chạy; còn store dựng tay thì quá đơn giản. Shopify Engineering giới thiệu ShopGym, framework biến storefront thật thành sandbox shop tự chứa, reset được, kèm bộ task gắn với sản phẩm, tính năng và policy của từng shop. Mục tiêu là reproduce lỗi và so sánh agent trong điều kiện cố định.

Thành phầnShopArena (sinh môi trường) · ShopGuru (sinh benchmark task)
Kiểm chứng224 task trên 6 sandbox shop (3 dữ liệu synthetic, 3 dữ liệu thật)
Loại task7 nhóm kỹ năng, từ tìm sản phẩm đến hành trình nhiều bước
Kết quảHiệu năng agent trên shop synthetic tương quan thuận với storefront thật
Công khaiPaper, repo open source, project site có shop mẫu

ShopArena: từ storefront thật đến sandbox

  • Pha khám phá: planner agent chia storefront (homepage, sitemap, endpoint search/cart, catalog public, trang policy) thành các task nhỏ. Mỗi task do một specification agent mới, có browser tool, thực hiện.
  • Kết quả là shop specification gồm design spec, thuộc tính có cấu trúc (filter, navigation, pagination) và thống kê catalog (số sản phẩm, phân bố giá). Agent bỏ tên thương hiệu, tên sản phẩm, tên người và URL tuyệt đối ngay khi viết nên không cần bước redact riêng.
  • Pha sinh chỉ đọc specification: tạo catalog hư cấu, rồi dựng shop theo thứ tự cố định gồm shell/homepage, collection, trang sản phẩm, cart, search/filter, policy, integration. Tính năng nào lỗi thì sửa riêng, không phải sinh lại cả shop.

Vòng lặp execution–verification

  • Mỗi bước dùng một execution agent mới, đọc code hiện tại, spec liên quan, catalog và feedback gần nhất; sửa code và chạy type check, build.
  • Rule-based check kiểm build, route bắt buộc, cấu trúc output. Sau đó một visual verification agent host shop, mở trình duyệt kiểm tra và ghi feedback cho vòng sau.
  • Agent mới cho mỗi vòng giữ context nhỏ: source code là state, spec là ý định, report gần nhất là việc cần sửa tiếp.

ShopGuru và kết quả đánh giá

  • Task đơn giản (tìm sản phẩm, tìm return policy) do generator rule-based sinh; hành trình nhiều bước (mở collection, lọc màu, sort giá, thêm vào cart) do LLM viết. Mọi sản phẩm, collection, filter được kiểm tra có tồn tại, sai thì LLM nhận feedback để sửa.
  • Về cấu trúc, shop synthetic có số state và độ phức tạp trang tương đương shop thật, nhưng ít liên kết hơn vì bỏ link ngoài và trang marketing.
  • Về hành vi (đánh giá bằng BrowserGym và một hệ thống nội bộ dùng screenshot), tỉ lệ thành công gần nhau, rõ nhất ở task nhiều bước, và giữ nguyên thứ hạng model. Một số task đơn có chênh lệch lớn hơn.
👉 Vì sao quan trọng: Shopify đang đầu tư nghiêm túc cho agent mua hàng thay người dùng. App can thiệp vào storefront (widget, popup, giảm giá, điểm thưởng) sẽ ngày càng bị agent 'đọc' chứ không chỉ người xem. Ngoài ra, mẫu 'agent mới mỗi vòng + spec là nguồn sự thật + verification agent' áp dụng được cho các tác vụ sinh code dài.
✅ Nên làm: Đọc paper/repo ShopGym. Thử để một browser agent làm vài task trên dev store có cài widget của app (tìm ưu đãi, áp mã) và xem widget có cản trở hay hỗ trợ agent không.

#3 🔴 Phải đọc · 🛠 Developer · — · ⭐⭐

Stripe/Metronome: token billing là hạ tầng tốt nhưng là cách tính giá tệ, hãy bán credit hoặc output Đọc sâu

Stripe (qua Metronome) có tính năng token billing: tính tiền khách theo lượng token model tiêu thụ cộng markup. Tác giả, người từng muốn khai tử tính năng này, giải thích vì sao vẫn giữ: nó hữu ích ở backend để theo dõi usage, quản lý markup và bảo vệ unit economics. Nhưng nếu đưa ra hoá đơn cho khách, bạn đang để chi phí quyết định giá bán. Theo tác giả, hoá đơn là nơi định nghĩa giá trị bạn mang lại cho khách.

Token billingGiữ ở backend: tracking usage, markup, margin
Unified creditsKhách trừ dần một quỹ credit chung, mỗi thao tác tốn số credit riêng
Output-basedTính theo đầu ra đếm được (ảnh tạo ra, email gửi, ticket đã giải quyết)
Hybrid pricingSeat + usage: ~1/6 user Stripe đã vượt mốc doanh thu đang dùng hoặc triển khai (8/2026)

Vấn đề của hoá đơn theo token

  • Hoá đơn ghi 10 model với markup 10%, 5%, 25%… tức là bạn tự định nghĩa giá trị của mình là phần chênh so với chi phí model của người khác.
  • Khi model rẻ đi và thay thế được cho nhau, khách sẽ mặc cả markup hoặc đi thẳng tới provider. Cạnh tranh đẩy markup, và có thể cả doanh nghiệp, về 0.
  • Nhiều khách của Metronome định tuyến model ở upstream, gửi token usage về Metronome để theo dõi chi phí và tinh chỉnh margin, nhưng vẫn cần một lớp trình bày khác cho khách.

Ba loại thước đo giá

  • Input (token): là chi phí, không phải giá trị.
  • Outcome (doanh thu tăng, churn giảm): theo tác giả gần như là 'myth', chỉ khả thi khi có quyền lực gần độc quyền hoặc hợp đồng đủ lớn để đo end-to-end. Ví dụ agent bán hàng tính theo doanh thu sẽ gây tranh cãi ngay: sale đó do agent, do sales rep hay do marketing?
  • Output: đếm được và kiểm chứng được. Fin tính theo hội thoại hỗ trợ đã được giải quyết, thường gọi là outcome nhưng thực ra là output. Lời khuyên: chọn output metric, gọi nó là outcome và thuyết phục thị trường.

Thị trường đổi rất nhanh khi đã đổi

  • Hybrid pricing được Metronome hỗ trợ từ 3 năm trước nhưng gần như không ai dùng trong ~18 tháng, rồi bùng lên.
  • Trong vòng một quý sau khi Fin tính giá theo hội thoại được giải quyết, cả 5 công ty dẫn đầu mảng AI support đều cam kết một dạng pricing tương tự.
  • Tác giả dự đoán khi agent vừa mua dịch vụ vừa làm việc, pricing có thể phức tạp hơn mức con người xử lý được (giống high-frequency trading), và output do agent tạo ra sẽ thành pricing metric.
👉 Vì sao quan trọng: App Shopify có usage fee hoặc tính năng AI đang phải chọn giữa tính theo order, theo lượt dùng hay theo plan. Bài này cho khung tư duy: đo chi phí chi tiết ở backend, nhưng hoá đơn hiển thị đơn vị merchant hiểu được giá trị (ví dụ số đơn được xử lý, số chiến dịch gửi đi).

#4 🟡 Nên biết · 🤖 AI · 🔥🔥🔥 · ⭐⭐

Strata: chạy Qwen 3.8 Flash Next (125B) trên PC gaming 12GB VRAM, có API tương thích Anthropic/OpenAI cho Claude Code và Codex Mới

Model MoE 125B thường cần server có hàng trăm GB VRAM. Strata (11k sao GitHub, 610 điểm HN) làm nó chạy được trên PC gaming NVIDIA/AMD 12GB VRAM trở lên bằng cách phân chia công việc cho toàn bộ máy, và expose API cục bộ để cắm thẳng vào coding agent. Repo nói RTX 3090 (24GB) dự kiến đạt khoảng 100–140 token/s khi sinh câu trả lời.

API/v1/messages (Anthropic) và /v1/responses (OpenAI) trên 127.0.0.1:8080

Cách nó vừa với PC thường

  • Model gồm 24.576 expert nhỏ, mỗi token chỉ dùng 10 expert. GPU giữ vài nghìn expert dùng nhiều nhất, RAM giữ toàn bộ và CPU xử lý phần còn lại song song; SSD chứa một bảng lookup lớn.
  • Speculative decoding: model phụ nhỏ đoán trước vài token, model lớn kiểm tra một lần, cho cùng kết quả nhanh hơn 1,6–1,8 lần.
  • Prompt dài được đọc theo khối tới 8.192 token, hơn 1.000 token/s. Tin nhắn đầu của chat mất khoảng 1 phút cho mỗi 30.000 token, các tin sau bắt đầu trong vài giây.

Dùng với coding agent

  • Claude Code: đặt ANTHROPIC_BASE_URL trỏ về Strata. Codex CLI dùng endpoint Responses API.
  • Có thể dán một câu prompt vào coding agent để nó tự kiểm tra GPU/RAM/ổ đĩa, chọn size model, cài và khởi chạy; Strata cũng có MCP server để agent bật/tắt.
  • Mặc định xử lý một request một lúc; muốn song song thì đặt parallel = 2, nhưng trên card 12GB mỗi câu trả lời sẽ chậm hơn. Truy cập từ máy khác phải đặt --api-key.

Lưu ý

  • Lần khởi động đầu máy có thể đơ 1–3 phút vì nạp 35–55GB vào RAM.
  • Bản Coder yếu hơn ngoài code, kể cả tiếng Trung và CJK. Bản Unsloth UD-Q4_K_XL gần model gốc nhất nhưng chỉ ~7–8,5 token/s trên máy 64GB vì đọc từ SSD.

Tính năng mới

  • Nối repo Artifacts với Worker qua Workers Builds: push lên production branch thì deploy, push nhánh khác thì tạo Workers Preview riêng.
  • Artifacts binding trong Worker: tạo/fork repo, đọc file và commit, cấp Git token theo phạm vi repo — ví dụ fork project cho mỗi task của agent rồi đọc AGENTS.md làm chỉ dẫn.
  • Event khi repo được tạo, import, fork, xoá, push, clone, fetch; subscribe để chạy CI hoặc khởi động review agent.
  • Chọn data jurisdiction US/EU theo namespace; dashboard có metrics thao tác, push/pull, lỗi.

Cách dùng hiện tại

  • Nền tảng vibe-coding lưu project người dùng; dev lưu code và context của session agent.
  • Tạo repo cô lập để nhiều agent cùng bắt đầu từ một điểm, so sánh hoặc merge kết quả sau.
  • Cloudflare không muốn 'GitHub hiện tại thêm agent' mà muốn nghĩ lại repo, branch, PR, worktree, review và merge conflict.

Vì sao dev né platform

  • Lịch sử: trình duyệt từng đi sau hệ sinh thái (jQuery lấp chỗ trống, phải chờ IE6 biến mất). Mãi đến khoảng 2020 web mới bớt 'lồi lõm'.

#8 🟢 Đọc thêm · 🏗 Software engineering · — · ⭐

ByteByteGo: SSH hoạt động ra sao, 6 kỹ thuật serve LLM hiệu quả và công thức eval 3 bước Đọc sâu

Số System Design Refresher tuần này gom vài chủ đề nền tảng ngắn gọn: luồng bắt tay SSH, các kỹ thuật giảm độ trễ và chi phí khi serve LLM, cấu trúc một AI agent và cách xây eval cho ứng dụng AI.

SSHTCP → thương lượng thuật toán → key exchange → kiểm host key với known_hosts → xác thực bằng chữ ký
Serve LLMStreaming, quantization, continuous batching, prefix caching, paged KV cache, speculative decoding
EvalChọn task → thu dữ liệu eval → xây grader (code / LLM-as-judge / người)

SSH

  • Server gửi public key và chữ ký, client kiểm tra rồi đối chiếu host key với known_hosts.
  • Hai bên tự tính cùng session key, không bao giờ gửi qua mạng. Client ký yêu cầu xác thực bằng private key, server kiểm chữ ký bằng public key trong authorized_keys; private key không rời máy.

Serve LLM và eval

  • Prefix caching bỏ qua phần tính toán của prefix prompt đã cache; paged KV cache cấp phát cache theo block cố định khi chuỗi dài ra; speculative decoding để model nhỏ đề xuất nhiều token, model chính kiểm tra trong một lượt forward.
  • Eval: dùng grader bằng code cho thứ có đáp án rõ (unit test), LLM-as-judge cho tiêu chí chủ quan, con người cho edge case. Production eval thường kết hợp cả ba.
👉 Vì sao quan trọng: Hiểu prefix caching giúp giải thích vì sao giữ prompt prefix ổn định thì gọi LLM API rẻ hơn. Công thức eval 3 bước áp dụng được ngay cho tính năng AI trong app.
